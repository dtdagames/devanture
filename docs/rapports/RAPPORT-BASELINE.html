1. Verdict

Sur un site vitrine de 6 pages produit en une passe, le DSL divise par 3,6 à 4,6 le volume écrit par le modèle et réduit de 18 à 32 % la consommation totale de tokens, pour un temps divisé par 1,5 à 2. En revanche, l'hypothèse « le compilateur fait converger là où le PHP direct échoue » n'est pas démontrée : les quatre sites écrits à la main sont sortis sans la moindre erreur PHP, du premier coup, et passent exactement le même banc de 46 contrôles que les sites générés. Avec les modèles actuels, un site de cette taille n'est pas un problème de correction, c'est un problème de volume, de temps et d'homogénéité.

Surprise de ce test : fournir la bibliothèque de composants aux agents a augmenté leur consommation de tokens par rapport à l'écriture sans bibliothèque, parce qu'ils ont lu les sources des composants pour en comprendre l'usage. La valeur du DSL tient moins aux composants qu'à la documentation compacte (catalog, explain) et à l'oracle de validation (check).

2. Protocole

Mêmes deux briefs que dans le premier test, mêmes modèles par brief (Sonnet pour le cabinet d'avocats, modèle par défaut pour la boulangerie). Quatre agents sans contexte, deux variantes :

  • Sans bibliothèque : PHP, JS et CSS écrits de zéro à partir d'un cahier des charges technique (baseline/SPEC.md) qui liste tout ce que le DSL produit : routeur compatible php -S, 404 réel, SEO par page, nav avec aria-current, menu mobile, variables CSS, dix types de blocs, formulaire avec CSRF, pot de miel, validation serveur, JSONL et mail(), échappement systématique.
  • Avec bibliothèque : même cahier des charges, plus le dossier baseline/lib-composants/ contenant exactement les templates PHP, helpers, CSS et JS que le compilateur émet, avec un README et les fiches de composants. Il reste à écrire le routeur, la mise en page et les pages.

Pour la vérification, les agents à la main avaient php -l et l'exécution CLI, pas de serveur. Les agents DSL avaient check. Chaque agent a tenu un journal. J'ai ensuite passé les six sites au même banc automatique (scripts/verify-php-site.mjs) : serveur PHP réel, toutes les routes, titres et descriptions, nav, 404, assets, menu mobile, variables CSS, CSRF, pot de miel, POST vide, POST rempli, stockage du message.

Interdictions : lire le code du compilateur, les exemples DSL, ou, pour la variante sans bibliothèque, la bibliothèque. Les tokens « écrits » excluent les fichiers copiés à l'identique depuis la bibliothèque (comparaison par empreinte).

4. Lecture des résultats

4.1 Pourquoi l'écart de consommation est plus faible que l'écart de volume

Un agent relit son contexte à chaque appel d'outil. Sur 15 à 30 appels, le contexte accumulé (cahier des charges, fichiers lus, sorties de commandes, propres écritures) pèse beaucoup plus que ce qui est écrit une fois. Le DSL réduit l'écriture par 4 mais ne réduit que modestement le nombre d'appels. Pour gagner davantage, il faut réduire les tours : par exemple écrire tout le site en un seul appel, ou fournir un retour de check si fiable que l'agent n'a pas besoin de relire ses fichiers.

4.2 Pourquoi la bibliothèque a coûté plus cher que rien

Les deux agents « avec bibliothèque » ont lu les templates PHP et les helpers pour comprendre les props et les variables globales attendues, malgré le README et les fiches. L'un d'eux l'écrit : les fiches étaient en YAML, pas en PHP, il a dû lire le code pour traduire. Une bibliothèque n'économise des tokens que si sa documentation suffit et si elle est plus courte que le code. C'est exactement ce que font catalog et explain dans le DSL, et c'est là que se situe le gain, pas dans les composants eux-mêmes.

4.3 L'oracle de validation

Aucun agent n'a fait d'erreur PHP, mais trois des quatre agents « à la main » ont perdu une passe de test entière à cause de leur propre harnais : conversion de chemins par Git Bash, inclusion du routeur depuis une fonction, sortie standard qui déclenchait « headers already sent ». Ils ont dû construire eux-mêmes leur moyen de vérifier, et ce moyen était faux au premier essai. Les agents DSL avaient check et n'ont rien eu à construire. Ce coût ne se voit pas dans la colonne « erreurs », il se voit dans les colonnes « appels », « tokens » et « durée ».

4.4 Ce qui n'est pas mesuré mais visible

  • Homogénéité. Les deux sites DSL ont exactement la même structure de fichiers, le même balisage, les mêmes classes. Les quatre sites à la main ont quatre architectures différentes (inc/blocks.php, lib/blocks.php, site.php, config.php…), quatre nommages du pot de miel, quatre routeurs. Pour maintenir un parc de sites, c'est l'écart le plus important.
  • Propagation des correctifs. Les deux failles de sécurité trouvées pendant ce test (section 5) ont été corrigées une fois dans le générateur et appliquées aux trois sites DSL par une recompilation. Les mêmes failles dans des sites écrits à la main demanderaient une intervention par site.

5. Qualité et sécurité

Deux failles dans le code que le générateur émettait, trouvées par les agents « avec bibliothèque » en lisant les helpers copiés, corrigées depuis :
  • Le destinataire du formulaire (_to) et la liste des champs obligatoires (_required) étaient lus depuis des champs cachés du POST, donc modifiables par le client : relais de spam possible et validation contournable. Ils sont désormais fixés côté serveur dans la table des routes.
  • Le routeur servait tout fichier existant, donc /data/messages.jsonl était téléchargeable. Seuls les assets sont servis maintenant, et data/, lib/, pages/, components/ reçoivent un .htaccess de refus.

À l'inverse, l'agent qui a écrit le Fournil sans bibliothèque avait confiné les fichiers statiques avec realpath dès sa première version. La qualité d'un générateur est un coût fixe payé une fois et audité une fois ; la qualité d'un site écrit à la main varie à chaque exécution et n'est auditée que si quelqu'un le fait. Aucun des quatre sites à la main n'a été audité au-delà du banc automatique.

Autres observations des agents sur la bibliothèque, non traitées : pas de prop id pour poser une ancre, hero sans variante compacte documentée, pas de lien d'évitement, CSS du menu mobile qui suppose un en-tête de 64 px, absence de limitation de débit sur le formulaire.

6. Enseignements pour la décision

  1. Le gain en tokens existe mais il est modeste sur une création unique : environ 20 % de la consommation totale, 4 fois moins de code écrit, 2 fois moins de temps. Il ne justifie pas à lui seul un compilateur si l'usage est « un site de temps en temps ».
  2. Le pari « convergence » doit être reformulé. Sur cette taille, les modèles actuels écrivent du PHP correct du premier coup. La valeur de check n'est pas de rattraper des erreurs de syntaxe, c'est de fournir un oracle prêt à l'emploi, ce qui évite à l'agent de construire et de déboguer son propre harnais. Il faudrait tester sur des modèles plus petits ou des sites plus complexes pour voir des erreurs réelles apparaître.
  3. La valeur se déplace vers la maintenance et le parc. Homogénéité, correctifs propagés par recompilation, modifications exprimées en quelques lignes de YAML. Rien de cela n'a été mesuré ici, et c'est pourtant le cœur de l'argument économique pour un éditeur de sites.
  4. La documentation compacte vaut plus que la bibliothèque. Si l'on ne construisait pas le DSL, il faudrait au minimum une bibliothèque documentée en PHP avec un exemple d'appel par composant et un script de vérification fourni, pour récupérer une partie du gain.

7. Correctifs appliqués au générateur pendant ce test

  • Destinataire et champs obligatoires du formulaire fixés côté serveur par route ; champs cachés _to et _required supprimés.
  • Service des fichiers statiques limité à /assets/ sous php -S et dans .htaccess ; .htaccess de refus dans les dossiers internes.
  • Méta description de repli sur l'accroche du site quand une page n'en déclare pas (trouvé par le banc sur mon propre site).
  • Lightbox : l'écouteur clavier est retiré à la fermeture par clic, pas seulement par Échap.

Le dossier baseline/lib-composants/ conserve volontairement la version avant correctifs, telle que les agents l'ont reçue.

8. Limites

  • Un essai par case : six agents, pas de variance. Un écart de 18 % peut être du bruit entre deux exécutions.
  • Les agents à la main n'avaient pas de serveur ; les agents DSL n'avaient pas build. Les deux côtés ont vérifié « à l'aveugle » du rendu réel. Le banc automatique a été appliqué après coup, à égalité.
  • Le cahier des charges a été écrit par moi à partir de ce que le DSL produit. Il est détaillé, ce qui avantage la variante à la main (pas d'ambiguïté) et la désavantage (beaucoup à implémenter). Un vrai client n'écrit pas un tel cahier des charges.
  • Qualité éditoriale et visuelle non évaluées, comme dans le premier test.
  • Tokens comptés avec un tokenizer approchant ; durées sensibles à la charge des serveurs au moment du test.
Mise à jour. Le test de maintenance (quatre modifications identiques sur les six sites) a été réalisé ensuite : voir RAPPORT-MAINTENANCE.html. Résumé : 25 à 36 % de tokens en moins et temps divisé par 2,3 à 2,7 avec le DSL, aucune régression, mais une modification sur quatre impossible faute de porte de sortie.

9. Suites

  1. Mesurer la maintenance, là où le DSL devrait creuser l'écart : sur chacun des six sites, demander à un agent trois modifications identiques (ajouter une section, changer le thème, ajouter un champ au formulaire) et comparer tokens, temps et régressions au banc.
  2. Tester un modèle plus petit (Haiku) sur les deux variantes : c'est là que des erreurs PHP réelles devraient apparaître et que check devrait faire la différence.
  3. Réduire les tours côté DSL : viser un site écrit en un seul appel, check compris, pour attaquer la part dominante du coût.
  4. Traiter les manques déjà listés dans le premier rapport : horaires, liste de prix, champs de formulaire typés, ancre par section.

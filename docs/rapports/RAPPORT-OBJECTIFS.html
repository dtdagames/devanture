Personnalisation, e-commerce minimal, agents comme visiteurs

Implémentés le 7 novembre 2026 dans le prototype Devanture · Les trois objectifs de la demande initiale sont désormais couverts · Suite de RAPPORT-NAVIGATION.html

1. Où en est le prototype

La demande de départ visait trois choses : un langage économe en tokens pour les LLM, des expériences adaptées à chaque visiteur, et des sites vitrines et e-commerce faciles à produire. Après cette passe, les trois sont couvertes dans le prototype : le DSL et son compilateur sont mesurés sur quatre tests, la personnalisation par segments et variantes est en place et vérifiée dans le navigateur, et une boutique complète, du catalogue à la confirmation de commande, se décrit en neuf fichiers YAML. S'y ajoute un point d'entrée pour les assistants qui agissent au nom des visiteurs. Le catalogue compte dix-huit composants.

2. Personnalisation par segments et variantes

Le modèle

Un fichier segments.yaml déclare des segments à conditions structurées, pas des expressions libres : nombre de visites, appareil, événements avec fenêtre temporelle, nombre d'occurrences et filtre, combinés par all, any, not, plus un ordre de priorité. N'importe quelle section accepte un bloc variants qui surcharge des props par segment. Le compilateur vérifie tout : événements connus, segments déclarés, variantes valides une fois fusionnées avec la base, interdiction de toucher à l'identifiant ou aux mots-clés.

segments:
  nouveau: { visits: 1 }
  recurrent: { visits: { gte: 2 } }
  devis_abandonne: { all: [ { event: form_start, within: 7d }, { not: { event: form_submit, within: 7d } } ] }
  fan_services: { event: section_view, where: { section: services }, count: { gte: 2 } }
priority: [devis_abandonne, fan_services, recurrent, nouveau]

- hero:
    title: Plombier chauffagiste à Lyon
    variants:
      devis_abandonne: { title: Votre demande de devis vous attend, cta: { label: Reprendre ma demande, to: /contact } }
      recurrent: { subtitle: Content de vous revoir. }

Le runtime

  • Une définition, deux évaluateurs. La spécification compilée est embarquée dans un module PHP et dans le JavaScript de la page, avec la même sémantique. Le PHP choisit la variante au premier rendu, donc sans scintillement et indexable ; le JavaScript tient le profil à jour.
  • Le profil reste chez le visiteur. Un cookie first-party contient des agrégats : nombre de sessions, compteurs et dernière date par événement, ventilés uniquement sur les clés que les segments utilisent. Le compilateur n'émet le suivi que des événements réellement référencés.
  • Consentement par défaut. Un bandeau demande l'accord avant toute écriture ; sans accord, aucun segment n'est actif et le site reste générique. Texte et activation configurables.
  • Mesure. Chaque variante affichée émet un événement vers un journal serveur, avec les segments actifs, pour comparer les conversions.

Le compteur de visites s'incrémente côté navigateur après le rendu : une variante liée au nombre de visites s'applique donc à partir de la page suivante de la nouvelle session, pas à la première. Les variantes liées aux événements s'appliquent dès la page suivante de l'événement. Il n'y a pas de remplacement de contenu en direct sans rechargement, c'est volontaire : le serveur reste la seule source du rendu.

3. E-commerce minimal

Le modèle

Un fichier data/products.yaml décrit les produits (identifiant, nom, prix numérique, catégorie, image, description, stock, badge, mise en avant). Six composants couvrent le parcours : products.grid (grille filtrée par catégorie ou mise en avant, tri, bouton d'ajout), une page dynamique /produit/[id] avec product.hero et products.related, cart.page, checkout.page, et une page dynamique /commande/[id] avec order.confirmation. Le compilateur vérifie la cohérence du parcours : des produits vendus sans panier, un panier sans commande ou une commande sans confirmation sont des erreurs nommées, avec la marche à suivre.

Le runtime

  • Panier en session PHP, actions par formulaires POST protégés par jeton, redirection vers la page d'origine, compteur dans l'en-tête, message de confirmation d'ajout.
  • Commande : validation des coordonnées, calcul des frais de port (forfait et seuil de gratuité), enregistrement dans un fichier JSONL avec identifiant et jeton d'accès, e-mail au commerçant et au client, vidage du panier, page de confirmation inaccessible sans le jeton.
  • Paiement : manual (à réception, virement, retrait) ou stripe via Stripe Checkout, la clé secrète dans un fichier .env jamais présent dans le DSL. Le mode Stripe est écrit mais non testé : ce poste n'a ni clé ni extension HTTPS en PHP. La confirmation après retour de Stripe n'est pas vérifiée côté serveur en v0 ; un webhook est nécessaire avant toute mise en production.
  • Les événements cart_add, checkout_start et purchase alimentent la personnalisation, ce qui rend possible le segment « panier abandonné » de la proposition.

Vérifié

Site de démonstration examples/savonnerie : neuf pages, six produits dont un épuisé. Un banc dédié de 31 contrôles joue le parcours complet sur serveur PHP réel : grille, fiche avec titre interpolé, fiche inconnue en 404, produit épuisé sans bouton, ajout refusé sans jeton, ajout de deux articles, sous-total exact, modification de quantité, retrait d'une ligne, frais de port, commande invalide avec erreurs par champ, commande valide, confirmation, confirmation sans jeton en 404, panier vidé, commande enregistrée et non servie en HTTP, produits exposés dans le jumeau. Le banc général passe ses 62 contrôles sur ce site.

4. Agents comme visiteurs

Le jumeau décrivait déjà le site ; il permet maintenant d'agir. GET /api/contact renvoie la définition des champs du formulaire et indique si l'API est active. POST /api/contact en JSON, avec un jeton porteur défini par le propriétaire dans .env, passe exactement la même validation que le formulaire, champs conditionnels compris, enregistre le message avec la source « agent » et l'envoie par e-mail. Vingt requêtes par heure et par adresse. Sans jeton configuré, l'API répond 503 ; avec un mauvais jeton, 401 ; au-delà du débit, 429. Le fichier d'instructions et les données structurées décrivent l'API, et la boutique y expose ses produits et ses routes.

5. Ce que vérifie le compilateur en plus

  • Segments : événement inconnu avec suggestion, durée mal formée, condition inconnue, segment inconnu dans la priorité ou dans une variante, variante invalide après fusion, variante qui touche à l'identifiant.
  • Produits : propriétés inconnues, identifiant mal formé ou en double, prix non numérique avec correction proposée, image absente, stock non entier.
  • Boutique : route dynamique mal formée, source manquante, composants de fiche hors de la page dynamique, panier ou commande ou confirmation absents, catégorie de filtre inconnue avec suggestion.

6. Limites et suites

  • Webhook Stripe (ajouté après ce rapport) : /_stripe/webhook vérifie la signature HMAC avec le secret du webhook, refuse une signature fausse ou un horodatage de plus de cinq minutes, passe la commande à « payée » sur session complétée, l'annule et libère le stock sur session expirée, ignore les autres événements, et répond 503 tant que le secret n'est pas configuré. Testé localement avec des événements signés par le banc (10 contrôles, 48 au total), rejeu idempotent compris. Reste non testé : la création de la session de paiement elle-même, qui exige une clé et une sortie HTTPS depuis PHP.
  • Stock (ajouté après ce rapport) : une réserve persistante data/stock.json tient le restant par produit ; l'ajout et la modification au panier sont plafonnés au restant avec un message ; la commande réserve toutes les lignes sous un seul verrou, et si le stock a changé entre-temps le panier est ajusté et le client prévenu ; la fiche et la grille affichent « Plus que N » sous trois unités puis « Épuisé ». Un réapprovisionnement dans products.yaml relance le restant. Les données d'exploitation (commandes, messages, stock, événements, .env) survivent désormais à une recompilation. Sept contrôles ajoutés au banc d'achat (38 au total).
  • Pas d'espace client ni de suivi : la confirmation est accessible par lien avec jeton, c'est tout.
  • Personnalisation sans mise à jour en direct : la variante s'applique au prochain rendu. Une version avec remplacement de section côté client demanderait d'émettre les variantes dans le HTML, au prix du poids des pages.
  • L'API couvre le formulaire de contact. Une commande par un agent demanderait un panier sans session navigateur et un paiement sans interface, hors périmètre pour l'instant.
  • Comme à chaque passe, mon propre YAML a déclenché le piège de la virgule une fois, et le message dédié l'a signalé du premier coup.
Mise à jour. Cinq chantiers de plus : relecture éditoriale à la compilation, assemblage des pages par segment, mémoire du visiteur, version texte avec lecture à voix haute, micro-sites par dérivation. Voir RAPPORT-CREATION.html.

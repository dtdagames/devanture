1. Verdict

En maintenance, l'écart se creuse en faveur du DSL : 25 à 36 % de tokens en moins, deux à trois fois moins de temps, deux fois moins d'appels d'outils, un diff deux fois plus petit, et aucune régression nulle part. Mais le DSL a échoué sur une des quatre modifications, l'ajout d'un champ au formulaire, parce que le composant ne le permet pas et qu'il n'existe aucune porte de sortie. Les quatre sites écrits à la main l'ont fait en 2 à 4 lignes. Le DSL est nettement plus économique pour tout ce qu'il couvre, et bloquant pour tout ce qu'il ne couvre pas.

2. Protocole

Les six sites des tests précédents ont été copiés dans maintenance/ (originaux conservés dans maintenance/originaux/). Six nouveaux agents sans contexte, un par site, mêmes modèles qu'avant (Sonnet pour le cabinet d'avocats, modèle par défaut pour la boulangerie), ont reçu quatre modifications décrites mot pour mot dans maintenance/MODIFICATIONS-*.md :

  1. M1 : ajouter une FAQ de trois questions données sur la page d'accueil, avant le dernier appel à l'action.
  2. M2 : changer le thème : couleur principale #6b2d5c, couleur d'accent #d4a017, titres en Georgia, partout.
  3. M3 : ajouter une page Recrutement : route, titre et description SEO, entrée de menu avant Contact, lien de pied de page, trois blocs au texte imposé.
  4. M4 : ajouter un champ facultatif « Entreprise » au formulaire, enregistré dans le JSON et dans le corps de l'e-mail.

Mêmes contraintes qu'avant : les agents DSL n'ont que CLAUDE.md, catalog, explain et check, sans build ; les agents PHP ont php -l et l'exécution en ligne de commande, sans serveur. Chaque agent devait dire si une modification était impossible plutôt que de contourner.

Vérification après coup, identique pour tous : un banc dédié aux quatre modifications (scripts/verify-maintenance.mjs, 28 contrôles : textes exacts présents, position de la FAQ, valeurs effectives des variables CSS dans l'ordre de cascade, page Recrutement, ordre du menu, champ et clé JSON), plus le banc de non-régression des tests précédents (51 contrôles, une page de plus). Le diff est mesuré entre original et copie modifiée, images exclues.

4. Lecture modification par modification

M1. Ajouter une FAQ

Équivalent partout : une dizaine de lignes, un composant existant. Les agents PHP ont lu le bloc FAQ existant et un exemple d'usage, les agents DSL ont imité une page voisine. Seule différence : deux agents PHP ont produit une erreur de syntaxe en échappant les apostrophes françaises dans des chaînes PHP, rattrapée par le linter. Le YAML en notation bloc n'a pas ce problème.

M2. Changer le thème

C'est la modification qui sépare le plus les approches. Dans le DSL, trois tokens dans site.yaml, par construction appliqués partout. À la main, les agents ont dû lire toute la feuille de style pour trouver ce que « accent » et « titres colorés » voulaient dire dans ce site-là, puis chasser les couleurs codées en dur : un dégradé de SVG, un favicon en ligne, une variable dérivée « primary-dark ». Deux des quatre sites en avaient. Chaque site écrit à la main a son propre vocabulaire de variables, et « accent » désignait un fond brun dans l'un, une couleur d'étoiles dans un autre. Le DSL impose un vocabulaire commun, ce qui rend la consigne non ambiguë.

Mais le DSL avait un trou, trouvé par les deux agents : les noms de tokens n'étaient ni documentés ni validés. Un agent a vérifié qu'un token inventé passait check sans erreur. Les deux ont deviné juste, mais un « ok » de check ne prouvait rien. Corrigé depuis (section 6).

M3. Ajouter une page

Simple partout, parce que les six sites ont une table de routes et un menu qui en dérive. Les agents PHP ont écrit une page en PHP et une ligne de route ; les agents DSL un fichier YAML et deux lignes dans site.yaml. Pas de différence de fiabilité ; différence de volume et de temps seulement.

M4. Ajouter un champ au formulaire

Échec du DSL. Le composant contact.form n'accepte qu'une liste fermée de cinq champs. Les deux agents l'ont constaté dans explain, confirmé par un check en erreur, restauré le fichier et déclaré la modification impossible, ce qui était le comportement demandé. Ils n'avaient aucun moyen d'agir : pas de champ libre, pas de bloc custom, pas d'accès au compilateur.

Les quatre sites PHP l'ont fait en 2 à 4 lignes. Deux d'entre eux avaient un formulaire piloté par une table de champs (ajout = une ligne), deux autres dupliquaient les libellés entre deux fichiers (ajout = trois endroits, source d'oubli signalée par les agents).

C'est la limite structurelle d'un DSL fermé : son coût est nul tant qu'on reste dans le catalogue, et infini dès qu'on en sort. La proposition prévoyait une porte de sortie (custom:) ; le prototype v0 ne l'a pas, et ce test montre qu'elle n'est pas optionnelle.

5. Enseignements

  1. En maintenance, le gain du DSL est plus net qu'à la création (25 à 36 % de tokens contre 18 à 19 %, temps divisé par 2,3 à 2,7 contre 1,5 à 2). Modifier demande de comprendre l'existant, et un site DSL se comprend en lisant 200 lignes de YAML homogènes au lieu de 400 à 1 600 lignes de PHP à l'architecture propre à chaque auteur.
  2. Le vocabulaire partagé vaut autant que la concision. « Couleur d'accent » n'a de sens que si le site a un token qui s'appelle ainsi. Sur les sites à la main, la même consigne a donné quatre interprétations.
  3. Un DSL sans porte de sortie bloque. M4 est une demande banale. Il faut au minimum des champs de formulaire déclaratifs libres, et un bloc custom pour le reste, avec un coût accepté : ce qui passe par custom n'est plus validé.
  4. La validation doit couvrir tout ce que l'agent peut écrire. Les tokens de thème non validés étaient un angle mort : check disait « ok » sur une faute de frappe. Chaque clé libre du DSL doit avoir une liste fermée ou une règle.
  5. Le linter PHP a suffi aux agents PHP : deux erreurs de syntaxe, deux détections immédiates, zéro régression au banc. L'argument « le compilateur rattrape les erreurs » reste non démontré ; l'argument « le compilateur rend le travail plus court et plus sûr par construction » se confirme.

6. Correctifs appliqués au compilateur

  • E_UNKNOWN_TOKEN : un nom de token de thème inconnu est une erreur, avec la liste des noms acceptés, une suggestion et un fix de renommage.
  • sitec explain site : fiche de site.yaml (props, presets, liste des tokens avec un exemple de valeur chacun). catalog et CLAUDE.md y renvoient.
  • Appliqués après la fin des deux agents DSL, pour ne pas modifier les conditions du test en cours.
Mise à jour, même jour. Les trois manques structurels ont été implémentés dans le compilateur après ce test :
  • Champs de formulaire libres : fields accepte des objets { name, label, type, required, options, placeholder } avec les types text, email, tel, number, date, select et textarea. Validation côté compilateur (noms, types, options, doublons, champs réservés) et côté serveur (e-mail, téléphone, nombre, date, choix dans la liste). La modification M4, impossible pour les deux agents DSL, tient désormais en une ligne : rejouée sur les deux sites DSL, elle passe 7/7 au banc, sans régression (51/51).
  • Bloc custom : inclut un fichier PHP du projet (plus CSS et JS optionnels, props libres). check vérifie que les fichiers existent et émet un avertissement W_CUSTOM ; le fichier est copié dans dist/custom/, jamais servi directement.
  • Prop id sur toute section : pose une ancre avant la section ; les liens /page#id sont validés sur la partie route.
Le site d'exemple examples/plomberie-martin utilise les trois (bandeau promo custom, formulaire avec entreprise, type de demande en liste et date, ancre « services » dans le menu) et passe le banc complet.

8. Limites

  • Un essai par case, pas de variance. Les écarts de temps sont aussi sensibles à la charge des serveurs.
  • Les agents DSL n'ont fait que trois modifications sur quatre : leur coût est donc légèrement sous-estimé par rapport à un DSL qui aurait permis M4.
  • M1 était ambiguë pour les sites qui avaient déjà une FAQ sur l'accueil (deux des six). Les agents ont tranché de la même façon ; le banc accepte les deux lectures.
  • M2 n'a pas été vérifiée visuellement, seulement par les valeurs effectives des variables CSS.
  • Le banc de non-régression ne couvre ni le JavaScript ni le rendu mobile réel.
Mise à jour. Le test de création a été rejoué sur Haiku : voir RAPPORT-HAIKU.html. Résumé : 44 à 46 % de tokens en moins et temps divisé par 4 avec le DSL, mais toujours zéro erreur PHP réelle chez les agents « à la main ».

9. Suites

  1. Ouvrir le formulaire : fields acceptant soit un nom connu, soit un objet { name, label, type, required } avec types texte, e-mail, téléphone, nombre, date, choix. C'est la cause de l'unique échec et une demande récurrente des trois tests.
  2. Bloc custom : un composant qui inclut un fichier PHP du projet, hors validation, avec un avertissement dans check. Sans lui, chaque besoin hors catalogue est un blocage.
  3. Prop id sur toute section, pour les ancres (demandée deux fois).
  4. Composants horaires et liste de prix, détournés dans les trois tests.
  5. Rejouer la maintenance sur Haiku, où des erreurs réelles devraient apparaître côté PHP et où la différence de fiabilité pourrait enfin se mesurer.

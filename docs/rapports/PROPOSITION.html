1. Thèse en une phrase

Ne pas inventer un langage généraliste. Construire un DSL déclaratif métier, écrit dans une syntaxe que les LLM connaissent déjà (YAML strict validé par un schéma), compilé par un compilateur strict aux erreurs actionnables vers du PHP et du JavaScript standard, avec la personnalisation comme concept natif mais résolue au runtime par des règles, jamais par un LLM à chaque requête.

2. Principes de conception

#PrincipeConséquence concrète
1Densité sémantique plutôt que syntaxe courteUne primitive = un bloc métier complet (catalogue, panier, formulaire). 20 lignes de DSL = 2 000 lignes de PHP/JS.
2Zéro apprentissage pour le modèleYAML + JSON Schema. Pas de parser maison en v1. Aucun symbole exotique.
3Le compilateur est le vrai produitChaque erreur dit : où, quoi, pourquoi, quelles valeurs sont acceptées, et propose une correction.
4Contexte à la demandeLe LLM ne charge jamais toute la doc. Il demande la fiche d'un composant quand il en a besoin (sitec explain hero).
5Personnalisation = segments + variantesDéclaratif dans le DSL, résolu côté serveur (SEO) et côté client (réactivité).
6Sortie standard, lisible, hébergeable partoutPHP 8.x sans framework lourd, JS vanilla ou léger, CSS avec design tokens. Compatible hébergement mutualisé.
7Porte de sortie toujours ouverteBloc custom: pour du PHP/JS brut quand le DSL ne suffit pas. Le DSL ne doit jamais bloquer.

Quatre briques :

  1. Le DSL : fichiers .site.yaml décrivant site, données, pages, sections, segments, variantes.
  2. Le compilateur sitec : Node/TypeScript. Valide, résout, émet.
  3. Le catalogue de composants : chaque composant = manifeste (props, slots, variantes, événements) + template PHP + module JS + CSS.
  4. Le runtime de personnalisation : collecte d'événements, calcul de segments, sélection de variantes. Une partie PHP, une partie JS, issues d'une même définition.

4. Le DSL

4.1 Structure d'un projet

mon-site/
  site.yaml            # identité, thème, langues, intégrations
  data/
    products.yaml      # ou products.source: csv | json | api
    collections.yaml
  pages/
    accueil.page.yaml
    produit.page.yaml  # page dynamique [slug]
    panier.page.yaml
  segments.yaml        # règles de segmentation
  custom/              # PHP/JS brut si besoin

4.2 site.yaml

site:
  name: Maison Dubois
  locale: fr-FR
  theme:
    preset: boutique-claire        # un des presets livrés
    tokens:                        # surcharges optionnelles
      color.primary: "#1F3A5F"
      font.heading: "Playfair Display"
  nav:
    - { label: Accueil, to: / }
    - { label: Boutique, to: /boutique }
    - { label: Contact, to: /contact }
  integrations:
    payment: { provider: stripe, mode: checkout }   # adaptateur, clés hors DSL (.env)
    email:   { provider: smtp }
    analytics: { provider: none }

4.3 Une page vitrine

page: accueil
route: /
seo: { title: Maison Dubois, description: Artisan savonnier depuis 1987 }
sections:
  - hero:
      title: Des savons faits main
      subtitle: Fabriqués en Provence
      image: hero.jpg
      cta: { label: Découvrir, to: /boutique }
  - features:
      items:
        - { icon: leaf, title: 100 % naturel, text: Huiles bio et locales }
        - { icon: truck, title: Livraison 48 h, text: Offerte dès 40 € }
  - products.grid:
      source: products
      filter: { featured: true }
      limit: 4
  - testimonials: { source: reviews, limit: 3 }
  - contact.form:
      fields: [name, email, message]
      to: contact@maisondubois.fr

4.4 Une page e-commerce dynamique

page: produit
route: /produit/[slug]
source: products          # fournit `product` au template
seo: { title: "{{ product.name }} | Maison Dubois" }
sections:
  - product.hero:
      gallery: product.images
      price: product.price
      stock: product.stock
      action: add-to-cart
  - product.details: { tabs: [description, composition, livraison] }
  - products.related:
      strategy: same-collection
      fallback: best-sellers
      limit: 4

Le panier et le checkout sont des pages fournies par le catalogue (cart.page, checkout.page) que l'on peut surcharger section par section.

4.5 Personnalisation native : segments et variantes

segments.yaml :

segments:
  nouveau:       { visits: { eq: 1 } }
  recurrent:     { visits: { gte: 2 } }
  panier_abandonne:
    all:
      - { event: add_to_cart, within: 7d }
      - { not: { event: purchase, within: 7d } }
  fan_savons:    { event: product_view, where: { collection: savons }, count: { gte: 3 } }
  mobile:        { device: mobile }

Variante sur n'importe quelle section :

  - hero:
      title: Des savons faits main
      cta: { label: Découvrir, to: /boutique }
      variants:
        nouveau:
          subtitle: "-10 % sur votre première commande avec BIENVENUE"
        panier_abandonne:
          title: Votre panier vous attend
          cta: { label: Reprendre mon panier, to: /panier }
        fan_savons:
          cta: { label: Nouveautés savons, to: /boutique/savons }

Règles :

  • Les conditions sont structurées, pas des expressions libres. Le compilateur peut tout vérifier et produire des erreurs précises.
  • Une section a toujours une valeur par défaut. Les variantes ne font que surcharger des props.
  • Priorité explicite si plusieurs segments correspondent : priority: [panier_abandonne, fan_savons, nouveau] au niveau du site, sinon ordre de déclaration.
  • Un LLM peut générer les textes des variantes à la compilation (optionnel). Jamais à la requête en v1.

4.6 Porte de sortie

  - custom:
      php: custom/promo-banner.php
      js:  custom/promo-banner.js
      props: { code: ETE2026 }

5. Le compilateur sitec

5.1 Pipeline

lecture YAML ─▶ validation JSON Schema ─▶ résolution (routes, sources, composants, segments)
            ─▶ vérifications sémantiques ─▶ IR (arbre de pages/sections typé)
            ─▶ émetteurs : PHP (rendu serveur, routage, données, sessions, panier)
                           JS  (hydratation, panier client, segments client, variantes)
                           CSS (tokens + composants utilisés uniquement)
            ─▶ manifeste de build (hash, pages, assets, dépendances)

5.2 Commandes

CommandeRôlePensée pour le LLM
sitec checkValidation sans émission, moins d'une secondeBoucle rapide, sortie JSON
sitec buildGénère dist/ (PHP + JS + CSS)Idempotent, reproductible
sitec explain <composant>Fiche du composant : props, types, exemples, variantesÉvite de charger toute la doc
sitec catalogListe compacte des composants (une ligne chacun)Environ 800 tokens pour tout le catalogue
sitec previewServeur PHP local + rechargementVérification visuelle
sitec diffCe qui change dans dist/ entre deux buildsRevue de changement

5.3 Format d'erreur

Chaque erreur est une ligne JSON, pensée pour être corrigée sans relecture de doc :

{
  "code": "E_UNKNOWN_PROP",
  "file": "pages/accueil.page.yaml",
  "path": "sections[2].products.grid.limite",
  "message": "Propriété inconnue `limite` sur `products.grid`.",
  "expected": ["source", "filter", "sort", "limit", "columns", "variants"],
  "hint": "Vouliez-vous dire `limit` ?",
  "fix": { "rename": { "from": "limite", "to": "limit" } }
}

Familles d'erreurs : schéma (prop inconnue, type), références (route, source, segment, image inexistants), sémantique (variante sans segment, deux pages même route, champ de formulaire sans destinataire), cohérence e-commerce (produit sans prix, paiement configuré sans page checkout).

Toute erreur a un fix applicable quand c'est possible. sitec check --fix applique les corrections sûres.

5.4 Pourquoi compiler et non interpréter

  • La validation statique est ce qui fait converger la boucle LLM. Interpréter repousse les erreurs à l'exécution, où le modèle ne les voit pas.
  • La sortie PHP/JS est lisible et déboguable par un humain. Pas de runtime propriétaire sur le serveur.
  • On émet uniquement le CSS et le JS des composants utilisés.

6. Le catalogue de composants

6.1 Manifeste

Chaque composant est un dossier :

components/products.grid/
  manifest.yaml     # props (JSON Schema), slots, variantes, events émis, exemples
  template.php      # rendu serveur
  module.js         # comportement client (optionnel)
  styles.css        # utilise les tokens, pas de couleur en dur
  README.md         # ce que renvoie `sitec explain`

Le manifeste est la source du schéma de validation et de la fiche explain. Une seule source de vérité.

6.2 Catalogue v1

FamilleComposants
Structurenav, footer, section, columns, spacer
Vitrinehero, features, gallery, testimonials, faq, team, cta, richtext, map
Formulairescontact.form, newsletter, quote.form (devis)
E-commerceproducts.grid, products.related, product.hero, product.details, collections.list, cart.summary, cart.page, checkout.page, order.confirmation
Donnéessources yaml, json, csv, api (REST en lecture), plus tard woocommerce, shopify
Intégrationsstripe (Checkout), paypal, smtp, webhook

6.3 Thèmes

Presets de design tokens (boutique-claire, atelier-sombre, minimal, ...) surchargeables. Les composants n'utilisent que des tokens. Un site a donc toujours une cohérence visuelle, même généré vite.

7. Runtime de personnalisation

7.1 Modèle d'événements

Événements standard, émis automatiquement par les composants :

page_view, product_view, add_to_cart, remove_from_cart, checkout_start, purchase, form_submit, search, click_cta.

Stockage v1 : cookie first-party chiffré + localStorage, agrégats seulement (compteurs, derniers événements, horodatages). Pas de base serveur obligatoire. Option profile.store: server plus tard (session PHP + table).

7.2 Résolution des segments

  • Une même définition (compilée depuis segments.yaml) produit segments.php et segments.js.
  • Côté serveur : le PHP lit le cookie, calcule les segments, rend la bonne variante. Le premier affichage est déjà personnalisé, sans flash, et indexable.
  • Côté client : le JS recalcule après chaque événement et peut mettre à jour les sections marquées live: true.

7.3 Garde-fous

  • Variantes bornées : on ne change que des props déclarées, jamais la structure ni le code. Pas d'injection possible.
  • Consentement : bandeau intégré, segments désactivés tant que non accepté (personalization.requires_consent: true).
  • Mesure : chaque variante affichée émet variant_shown, exploitable pour comparer les conversions.

7.4 Rôle du LLM dans la personnalisation

À la compilation uniquement : proposer des segments pertinents pour le métier, rédiger les textes des variantes, suggérer des règles. Le résultat est écrit dans le YAML, relu, versionné. Rien de généré à la requête en v1.

8. Protocole LLM

Objectif : qu'un agent produise un site fonctionnel avec le moins de tokens et d'itérations possible.

  1. Amorce : un CLAUDE.md d'une page livré avec le projet (règles, commandes, 3 exemples). Environ 600 tokens.
  2. Découverte : sitec catalog (liste compacte), puis sitec explain <composant> uniquement pour ceux utilisés.
  3. Écriture : fichiers .site.yaml.
  4. Boucle : sitec check, erreurs JSON, correction, check à nouveau. Objectif : convergence en 1 à 2 itérations.
  5. Vérification : sitec build puis sitec preview, capture d'écran si l'agent dispose d'un navigateur.
Budget cible pour un site vitrine de 5 pages : moins de 15 000 tokens au total. À comparer avec la baseline mesurée en phase 0 (ordre de grandeur attendu en PHP/JS direct avec reprises : 80 000 à 150 000).

9. Sortie générée (dist/)

dist/
  index.php            # routeur minimal (ou .htaccess + front controller)
  pages/*.php
  components/*.php
  lib/
    router.php, render.php, data.php, cart.php, segments.php, payment-stripe.php
  assets/
    site.css           # tokens + composants utilisés

Contraintes : PHP 8.1 ou plus, aucune dépendance Composer obligatoire en v1, fonctionne sur hébergement mutualisé classique.

11. Indicateurs

  • Tokens par site fonctionnel (entrée + sortie, toutes itérations).
  • Nombre d'itérations check avant zéro erreur.
  • Taux d'erreurs corrigées du premier coup grâce au hint ou au fix.
  • Part des besoins couverts sans bloc custom: (cible : plus de 90 % sur sites vitrines, plus de 75 % en e-commerce).
  • Temps humain de relecture avant mise en ligne.

12. Risques et parades

RisqueParade
Plafond d'expressivité du DSLBloc custom: dès la v1, et chaque usage de custom est remonté comme candidat à un nouveau composant.
Coût de maintenance du compilateurManifestes comme source unique. Ajouter un composant ne touche pas le cœur.
Qualité visuelle moyenneThèmes par tokens, composants dessinés par un designer, pas par le LLM.
Sécurité (formulaires, panier, paiement)Paiement délégué à Stripe Checkout, échappement systématique dans les templates, CSRF intégré au routeur, aucune valeur libre interprétée en PHP.
Dérive de la personnalisation (vie privée)Agrégats first-party uniquement, consentement, segments auditables en YAML.

13. Décisions ouvertes

  1. YAML ou JSON pour les fichiers source ? YAML est plus dense et plus lisible, JSON est sans ambiguïté. Recommandation : YAML en entrée, JSON Schema pour la validation, les deux acceptés.
  2. Stack du compilateur : Node/TypeScript (cohérent avec le nom du dossier, écosystème JSON Schema mature). PHP possible mais moins outillé pour le schéma.
  3. Stockage du profil utilisateur en v1 : cookie seul ou session serveur ? Recommandation : cookie seul, serveur en option en phase 3.
  4. Stripe Checkout (redirection, simple) ou Payment Element (intégré, plus de code) ? Recommandation : Checkout en v1.

14. Premières étapes concrètes

  1. Écrire les 3 sites de référence de la phase 0 et mesurer la baseline.
  2. Rédiger le JSON Schema de site.yaml et d'une page avec 4 composants (hero, features, products.grid, contact.form).
  3. Implémenter sitec check avec le format d'erreur de la section 5.3.
  4. Faire produire une page par un LLM avec uniquement CLAUDE.md, catalog et explain. Compter les tokens et les itérations.
  5. Seulement ensuite, écrire l'émetteur PHP.

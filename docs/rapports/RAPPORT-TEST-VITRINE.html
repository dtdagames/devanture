1. Verdict

La méthode fonctionne sur le périmètre vitrine. Deux agents sans aucun contexte, l'un sur le modèle par défaut, l'autre sur Sonnet, ont chacun produit un site de 6 pages valide dès la première exécution de check, avec pour seule documentation un mode d'emploi de 857 tokens, la liste du catalogue (413 tokens) et les fiches des composants utilisés (environ 160 tokens chacune). Le code PHP, JS et CSS généré représente 2,6 à 4,5 fois le volume du DSL écrit, compile sans erreur sur un PHP 8.3 minimal, et les sites s'affichent et fonctionnent, formulaire compris.

Mise à jour. La baseline (même site écrit à la main, avec et sans bibliothèque) a été réalisée ensuite : voir RAPPORT-BASELINE.html. 2. Question testée et protocole

La proposition repose sur trois paris : un DSL de haut niveau réduit ce que le LLM écrit, une syntaxe connue (YAML + schéma) ne demande aucun apprentissage, et un compilateur strict aux erreurs actionnables fait converger la boucle en une ou deux itérations. Le test cherche à vérifier le troisième pari surtout, les deux autres en passant.

Protocole

  1. Construire un prototype minimal du compilateur et un catalogue de 10 composants vitrine.
  2. Écrire moi-même un premier site (plombier à Lyon) pour valider le pipeline de bout en bout, prévisualiser sous PHP et tester le formulaire.
  3. Lancer deux agents sans accès à cette conversation ni au code source, avec un brief client chacun. Ils n'ont droit qu'à CLAUDE.md, catalog, explain et check. Ils tiennent un journal de chaque exécution de check et rapportent ce qui leur a manqué.
  4. Vérifier leurs sites indépendamment (check, build, lint PHP, HTTP 200 sur toutes les routes), mesurer les tokens, injecter des erreurs pour juger les messages.

5. Qualité des messages d'erreur

Projet volontairement cassé avec dix erreurs typiques : preset inexistant, route inconnue dans la nav, composant mal orthographié, prop mal orthographiée, prop obligatoire absente, image absente, valeur hors énumération, liste trop courte, lien vers une page inexistante, e-mail invalide. Les dix sont détectées, chacune avec le chemin exact dans le document. Quatre arrivent avec un fix mécanique.

E_UNKNOWN_COMPONENT  sections[0]              Vouliez-vous dire hero ?    fix: rename heros → hero
E_UNKNOWN_PROP       sections[1].hero.titre   Vouliez-vous dire title ?   fix: rename titre → title
E_ENUM               sections[1].hero.align   Vouliez-vous dire center ?  fix: set center
E_MISSING_ASSET      sections[1].hero.image   Ajoutez le fichier dans assets/ ou corrigez le chemin.
E_UNKNOWN_ROUTE      sections[3].cta.button.to  expected: ["/"]  Créez la page ou utilisez une URL complète.
…
Trois défauts trouvés, tous corrigés depuis (section 8).
  • Cascade après une erreur YAML. Une page illisible faisait disparaître sa route, donc check signalait en plus « route / inconnue » et « pas de page d'accueil ». Un agent qui suit les indices à la lettre aurait tourné en rond.
  • Faux amis dans les suggestions. Le seuil de distance d'édition proposait foo → to et date → name, avec un fix qui aurait écrasé une valeur correcte.
  • Message YAML brut. L'erreur du parseur était recopiée en anglais, sans extrait de la ligne fautive ni indication du vrai piège (deux-points ou virgule dans un texte en notation { }).

6. Enseignements

6.1 Le piège n° 1 n'est pas le DSL, c'est YAML

Mon propre premier check a renvoyé 44 erreurs. Toutes avaient deux causes : des virgules dans des textes écrits en notation compacte { a: x, b: y }, que YAML découpe en clés parasites, et des nombres lus comme des nombres là où un texte était attendu. Le validateur a tout attrapé, mais avec des messages génériques. Il a fallu un indice spécifique (E_UNQUOTED_COMMA) et une règle dans CLAUDE.md. Après cela, aucun des deux agents n'est tombé dedans. J'ai moi-même refait la même erreur dans six descriptions de manifestes, ce qui tronquait la doc de contact.form : un garde-fou refuse maintenant tout manifeste contenant une clé inattendue.

Conséquence pour la proposition : le choix de YAML reste bon pour la densité, mais la notation compacte doit être découragée pour tout texte, et le compilateur doit nommer ce piège explicitement. JSON éliminerait le problème au prix de 20 à 30 % de tokens en plus.

6.2 La convergence en une itération tient

Le pari central est vérifié sur ce périmètre : zéro erreur au premier check pour les deux agents, sur un DSL qu'ils découvraient. Trois facteurs y contribuent, et il faut les préserver quand le catalogue grossira : la fiche explain donne les valeurs exactes acceptées, les exemples des manifestes sont copiables tels quels, et le mode d'emploi nomme les pièges plutôt que les règles générales.

6.3 Le code généré doit viser le PHP le plus pauvre

Le PHP installé pour le test n'a pas l'extension mbstring. Deux templates l'utilisaient, ce qui plantait une page. C'est précisément le cas d'un hébergement mutualisé bas de gamme. Règle adoptée : aucune extension optionnelle dans le code émis, des helpers avec repli, et un lint PHP de la sortie sur un binaire minimal fait partie du pipeline.

6.4 Ce que les agents ont fait d'eux-mêmes

  • Lire tout le catalogue d'un coup plutôt qu'à la demande (2 863 tokens, négligeable).
  • Refuser d'inventer des témoignages pour un cabinet d'avocats, par déontologie, sans qu'on le leur ait demandé.
  • Détourner des composants quand il en manquait un : stats pour des horaires, features pour des villes d'intervention, quatre richtext pour une carte de produits. Le site reste valide mais plat. C'est le signal le plus utile pour prioriser le catalogue.

8. Correctifs appliqués pendant le test

  • E_UNQUOTED_COMMA : une clé inconnue qui ressemble à du texte est signalée comme virgule non protégée, avec la parade.
  • E_TYPE nombre reçu pour un texte : indice « mettez entre guillemets » et fix automatique.
  • stats.value accepte texte ou nombre.
  • Plus de mb_* dans le PHP émis : helpers first_letter() et str_cut() avec repli sans mbstring.
  • Erreur YAML : message en français, extrait de la ligne fautive, indice ciblé sur le piège { }, et suppression des erreurs de route en cascade tant qu'une page n'est pas lisible.
  • Seuil de suggestion plus strict : distance 1 jusqu'à 4 caractères, 2 jusqu'à 8, 3 au-delà. Plus de date → name.
  • explain : affiche lien { label*, to* }, liste parmi : a | b | c, et les types multiples.
  • Garde-fou de manifeste : toute clé inattendue dans un schéma fait échouer le chargement du catalogue avec un message explicite. Six descriptions fautives corrigées.
  • CLAUDE.md : piège YAML, format des liens, props de site.yaml, format tel:.

9. Limites de ce test

  • Pas de baseline. On ne sait pas combien de tokens et d'itérations un agent aurait mis pour produire le même site en PHP/JS direct avec une bibliothèque de composants. C'est la phase 0 de la proposition, toujours à faire. Sans elle, le gain de la couche DSL n'est pas démontré, seulement rendu plausible.
  • Un seul essai par modèle. Deux agents, un site chacun. La variance n'est pas mesurée.
  • Périmètre vitrine minimal. Pas de e-commerce, pas de personnalisation, pas de données externes, pas de multilingue. Les hypothèses de la proposition sur ces points restent non testées.
  • Qualité éditoriale et visuelle non évaluée. Les sites sont valides et s'affichent correctement, mais personne n'a jugé les textes ni le design.
  • Le formulaire envoie par mail(). Testé seulement pour le stockage JSONL et la validation. Aucun envoi réel vérifié.
  • Le tokenizer utilisé pour les mesures n'est pas celui de Claude. Les écarts relatifs sont fiables, les valeurs absolues approximatives.

10. Suites proposées

  1. Faire la baseline : donner les trois mêmes briefs à des agents sans DSL, avec pour seule aide une bibliothèque de composants PHP, et mesurer tokens, itérations, erreurs PHP à l'exécution. C'est la mesure qui manque pour décider.
  2. Trois composants issus des détournements observés : hours, pricelist, et des champs de formulaire typés (date, nombre, choix). Puis map et steps.
  3. Balisage léger dans richtext : gras, italique, liens, listes, via un sous-ensemble Markdown échappé.
  4. Répéter le test sur 5 briefs et 2 modèles, pour avoir une variance et vérifier que la convergence en une itération tient avec un catalogue de 15 composants.
  5. Décider YAML strict ou JSON à la lumière du piège des virgules. Mon avis : garder YAML, interdire la notation compacte pour les textes dans le mode d'emploi, et détecter le cas au compilateur, ce qui est fait.

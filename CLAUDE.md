# Devanture — mode d'emploi pour l'agent

Tu écris des sites vitrines dans un DSL YAML. Tu n'écris jamais de PHP, JS ou CSS : le compilateur `sitec` les génère.

## Commandes (depuis la racine du dépôt)

```
node bin/sitec.js catalog              # liste des composants (1 ligne chacun)
node bin/sitec.js explain <composant>  # props détaillées + exemple
node bin/sitec.js check <dossier>      # valide, erreurs en JSON (1 par ligne), code 1 si erreurs
node bin/sitec.js build <dossier>      # valide puis génère <dossier>/dist (PHP + JS + CSS)
```

## Structure d'un site

```
<dossier>/
  site.yaml              # identité, nav, thème, coordonnées
  pages/<id>.page.yaml   # une page par fichier
  assets/                # images référencées par les composants (chemin relatif à assets/)
```

### site.yaml

<!-- sitec: site.yaml -->
```yaml
language: 1                            # version du langage
site:
  name: Plomberie Martin               # obligatoire
  tagline: Dépannage 7j/7 à Lyon
  locale: fr-FR
  theme: { preset: clair }             # clair | sombre | chaleureux ; tokens: { color.primary: "#123456" } pour surcharger
  nav:
    - { label: Accueil, to: / }
    - { label: Services, to: /services }
  footer: { text: SIRET 123 456 789, links: [ { label: Mentions légales, to: /mentions-legales } ] }
  contact: { email: contact@exemple.fr, phone: 04 00 00 00 00, address: "12 rue des Lilas, 69003 Lyon" }
```

### pages/<id>.page.yaml

<!-- sitec: pages/accueil.page.yaml -->
```yaml
page: accueil
route: /                               # obligatoire, unique ; la page d'accueil a route: /
seo: { title: Plomberie Martin, description: "Plombier à Lyon, dépannage 7j/7" }
sections:                              # liste de sections ; chaque section = UNE clé (le composant) avec ses props
  - hero: { title: Plombier à Lyon, cta: { label: Appeler, to: "tel:+33400000000" } }
  - features:
      items:
        - { icon: clock, title: Intervention en 1 h }
        - { icon: shield, title: Devis gratuit }
```

## Règles

- Une section = un objet avec une seule clé, le nom du composant. Les props sont dessous.
- **Piège YAML n° 1** : en notation `{ a: x, b: y }`, une virgule ou un deux-points dans un texte coupe la valeur. Pour tout texte long (phrases, listes dans une phrase, « 4,9/5 »), utilisez la notation bloc ou des guillemets :
  <!-- sitec: fragment faq.items -->
  ```yaml
  - { q: Livrez-vous partout ?, a: "Oui, sous 48 h, en France métropolitaine." }
  - q: Livrez-vous partout ?
    a: Oui, sous 48 h, en France métropolitaine.
  ```
- Les valeurs qui ressemblent à des nombres mais sont du texte (années, « 6 », « 0 ») : entre guillemets quand la prop attend un string.
- Un lien (`cta`, `secondary`, `button`, `link`, entrées de `nav`) est toujours `{ label: Texte, to: cible }`, les deux obligatoires. `to` est une route déclarée par une page (`/contact`), une ancre (`#contact`), ou `https://…`, `mailto:…`, `tel:+33472001122` (format international conseillé).
- `site.yaml` accepte : `name*`, `tagline`, `locale`, `theme { preset, tokens }`, `nav [liens]`, `footer { text, links [liens] }`, `contact { email, phone, address }`, et les réglages décrits plus bas : `intent`, `agents`, `personalization`, `images`, `static`, `offline`, `studio`, `shop`. Rien d'autre (pas d'horaires structurés, pas de sous-menus en v0). Détail et liste des tokens de thème (`color.primary`, `color.accent`, `font.heading`, …) : `node bin/sitec.js explain site`. Un token inconnu est une erreur.
- Les images sont des fichiers existants dans `assets/`. Si tu n'as pas d'image, n'en référence pas. Dépose les photos en JPEG, PNG ou WebP à leur taille d'origine : le compilateur produit les variantes WebP redimensionnées (480, 960, 1600 px par défaut), le `srcset`, les attributs `width`/`height` et le chargement différé. Réglage : `site.images: { widths: [...], quality: 80 }` ou `{ enabled: false }`. Les SVG sont copiés tels quels.
- **Formulaire** : `fields` mélange noms connus (`name`, `email`, `phone`, `subject`, `message`) et champs libres `{ name: company, label: Entreprise, type: text }` (types : text, email, tel, number, date, select avec `options`, textarea ; `required: true` possible). Voir `explain contact.form`.
- **Ancre** : toute section accepte `id: mon-ancre` ; on y pointe avec `to: /page#mon-ancre` ou `to: "#mon-ancre"`. **Piège YAML n° 2** : un `#` précédé d'un espace commence un commentaire, donc une ancre seule s'écrit toujours entre guillemets (`"#contact"`), de même qu'une couleur (`"#6b2d5c"`).
- **Champ conditionnel** : un champ libre accepte `when: { autre_champ: valeur }` ou `when: { autre_champ: [v1, v2] }` ; il n'est affiché et validé que si la condition est vraie. Le champ conditionnant doit être déclaré avant (typiquement un `select`).
- **Navigation par intention** : le compilateur indexe chaque section (titre, textes, questions de FAQ) et l'en-tête reçoit un champ « Que cherchez-vous ? » qui renvoie à la section exacte. Ajoutez `keywords: [mots, questions]` sur une section pour l'aider (ex. `keywords: [urgence, fuite, nuit]`). Réglage : `site.intent: { enabled: true, placeholder: … }`. Pour faire proposer les mots-clés par un modèle et les figer dans le YAML : `node bin/sitec.js keywords <dossier>` (clé d'API Anthropic requise ; sinon `--export f.json`, réponse d'un modèle, puis `--import f.json`).
- **Jumeau pour agents** : le site compilé expose `/site.json` (données structurées : pages, horaires, tarifs, formulaires et leur protocole) et `/llms.txt` (instructions lisibles), plus un JSON-LD dans chaque page. Réglage : `site.agents: { enabled: true, summary: une phrase, business_type: LocalBusiness | Bakery | LegalService | Plumber | Restaurant | … }`.
- **Personnalisation** : `segments.yaml` à la racine déclare des segments (`visits`, `device`, `event` avec `within`, `count`, `where`, combinés par `all` / `any` / `not`) et une `priority`. Toute section accepte `variants: { nom_de_segment: { props surchargées } }` ; la première variante dont le segment est actif s'applique au rendu serveur. Le profil du visiteur reste dans son navigateur (cookie first-party), avec un bandeau de consentement par défaut. Détail : `explain site`. Les variantes ne changent jamais `id`, `keywords` ni `variants`.
- **Boutique** : `data/products.yaml` (`products: [ { id, name, price (nombre), category, image, description, stock, badge, featured, unit } ]`) ; composants `products.grid` (grille filtrée), page dynamique `route: /produit/[id]` avec `source: products` et `product.hero` (+ `products.related`), `cart.page` (une seule), `checkout.page` (une seule), page `route: /commande/[id]` avec `source: orders` et `order.confirmation`. Réglages : `site.shop: { currency, payment: manual | stripe, manual_instructions, shipping: { flat, free_from }, order_email }`. `check` vérifie que panier, commande et confirmation sont tous présents. Les clés (Stripe, jeton d'API) vont dans `.env`, jamais dans le YAML : `STRIPE_SECRET_KEY` pour créer les paiements, `STRIPE_WEBHOOK_SECRET` pour le webhook `/_stripe/webhook` qui confirme (payée) ou annule (session expirée, stock libéré) les commandes. Le stock se décrémente à la commande ; un réapprovisionnement se fait dans `products.yaml`.
- **Expériences** : une variante ne vaut que si elle sert, et cela se mesure. `segments.yaml` accepte `goals: { appel: { event: click_cta, where: { to: "tel:+33472001122" } }, devis: { event: form_sent, where: { form: contact } } }` (ce qu'on cherche à obtenir ; `form_sent` = formulaire accepté par le serveur) et `experiments:`, sous deux formes. A/B : `accroche: { goal: appel, arms: [urgence] }`, où `urgence` est un nom neuf (pas un segment) employé dans `variants:` comme un nom de segment. Variante d'un segment : `relance: { goal: devis, segment: devis_abandonne, holdout: 20 }`, où 20 % du segment gardent le contenu de base. Dans les deux cas un groupe témoin tiré au sort (`temoin`, nom réservé) voit le contenu de base ; `minimum: 200` visiteurs par groupe avant tout verdict. Un bras sans variante dans les pages est une erreur. Résultat dans le back-office, onglet « Expériences » : fait mieux, fait moins bien, pas de différence mesurable, pas assez de données. Retire la variante que le verdict donne sans effet. Détail : `explain site`.
- **Assemblage par segment** : au niveau d'une page, `variants: { segment: { first: [ids de sections], hide: [ids] } }` réordonne ou masque des sections (qui doivent avoir un `id`) pour le premier segment actif.
- **Mémoire du visiteur** : le composant `recent` affiche les produits et sections consultés récemment (profil navigateur, consentement requis) et n'affiche rien sans historique.
- **Version texte** : chaque page statique existe aussi en `/lisible<route>`, texte simplifié avec lecture à voix haute ; lien « Version texte » dans le pied de page, généré automatiquement.
- **Page dérivée (micro-site)** : `extends: <id de page>` puis `override: { id_section: { props } }`, `remove: [ids]`, `prepend: [sections]`, `append: [sections]` ; `route` et `seo` propres. Une page dérivée n'a pas de `sections`.
- **Relecture éditoriale** : mettez le brief du client dans `brief.md` à la racine du site. `node bin/sitec.js review <dossier>` liste les faits chiffrés absents du brief, les engagements (délais, garanties, gratuité, certifications) à faire valider et les textes « à compléter ». Un texte `[à compléter]` fait échouer `build` (sauf `--draft`). N'invente ni prix, ni délai, ni distinction : si le brief ne le dit pas, écris `[à compléter]`.
- **Version du langage** : `language: 1` en tête de `site.yaml` (racine, hors du bloc `site`). Spécification : `docs/LANGAGE.md`, résumé : `node bin/sitec.js explain langage`.
- **Expressions** `{{ … }}` dans toute valeur texte : `{{ site.contact.phone }}`, `{{ const.delai }}`, `{{ collections.realisations | count }}`, `{{ page.title }}`. Opérateurs `+ - * / % ~ == != < > and or not in`, filtres `| upper | money | date('F Y') | join(', ') | default(x) | truncate(n)`… (liste : `explain langage`). Les filtres se lient avant les opérateurs : `(a * 1.2) | money`. Une clé inconnue sous `site` ou `const` est une erreur. **Piège YAML n° 3** : une valeur qui commence par `{{` s'écrit entre guillemets (`"{{ item.title }}"`), sinon YAML lit un objet.
- **Constantes** : `constants: { delai: 1 h, zone: Lyon }` à la racine de `site.yaml`, lues par `{{ const.delai }}`. Un chiffre répété (délai, tarif, zone) va là, une seule fois.
- **Collections** : à la racine de `site.yaml`, `collections: { realisations: { label, fields: { title: { type: string, required: true }, image: asset, date: date, category: string, text: text }, sort: -date } }` ; éléments dans `data/realisations.yaml` sous la clé `realisations:` avec un `id` unique (minuscules, chiffres, tirets). Types : string, text, number, boolean, date (`"2026-09"`), asset, list, link. Page par élément : `route: /realisations/[id]`, `source: realisations`, et `item.*` dans ses props et son `seo` (`"{{ item.title }}"`, `"{{ item.date | date('F Y') }}"`). Liste : `collection.list` (`source`, `filter: { category: x }`, `sort`, `limit`, `columns`). Noms réservés : products, orders, messages, events, stock.
- **Composants composés** (`components.yaml` à la racine) : `components: { offre: { description, params: { titre: { type: string, required: true }, points: { type: list, default: [] } }, sections: [ - pricelist: { title: "{{ p.titre }}" }, - features: { items: { for: p.points, as: pt, item: { icon: check, title: "{{ pt }}" } } } ] } }`. Usage dans une page comme un composant natif : `- offre: { titre: Dépannage, points: [Rapide, Garanti] }`. Types de paramètre : string, text, number, boolean, list, object, link, asset. Pas de `variants` sur un assemblage. Fiche : `explain offre <dossier>`.
- **Composant au format langage** (le format par défaut) : un seul `manifest.yaml`, quatre blocs, avec `données` (« title: texte, facultatif — description », « items (liste, au moins 1): » puis les champs ; types texte, nombre entier, oui ou non, lien, image, icône, date ; précisions facultatif, au moins N, de A à B, un parmi a, b), `forme` (primitives : en-tête, titre, titre principal, texte, texte discret, paragraphes, citation, image, icône, étoiles, signature, bouton, carte, témoignage, grille de x, liste de x, défilement de x, onglets de x, accordéon de x, filtres de x selon champ, repli, image agrandissable, portrait, copier, figure, si, sinon, formulaire + champ ; un nom « » donne une classe ; les comportements viennent avec la primitive ; les mots du vocabulaire s'emploient comme des primitives), `apparence` (« cartes: compactes, coins arrondis », « sur téléphone: »), `fonctionnement` (« formulaire: » avec « enregistre dans: devis », « prévient par e-mail: oui », « confirmation: … », « champs: » puis un champ par ligne « nom: type, précisions — Libellé (ex. exemple) » ; types texte, texte long, e-mail, téléphone, nombre, date, choix ; précisions facultatif, si champ vaut valeur, un parmi a, b en dernier ; name, email, phone, subject, message sont connus ; la forme place le formulaire par « - formulaire, bouton Envoyer »). Ni HTML, ni CSS, ni JavaScript. Une erreur renvoie à la ligne du manifeste (`"path":"ligne 21"`) ; `node bin/sitec.js component show <dossier> <nom>` montre chaque bloc et ce qu'il produit (schéma, effets, gabarit, feuille ; `--php` pour le PHP exécuté). Détail et listes : `node bin/sitec.js explain langage`, `docs/LANGAGE.md` section 6. Les composants natifs `hero`, `richtext`, `gallery`, `pricelist`, `map`, `collection.list`, `features`, `stats`, `steps`, `testimonials`, `faq`, `timeline`, `cta`, `team`, `hours`, `recent`, `contact.form`, `products.grid`, `product.hero`, `products.related`, `cart.page`, `checkout.page`, `order.confirmation` sont écrits ainsi : modèles à suivre.
- **Lecture à la visite** (stock, panier, horaires du moment) : dans le manifeste, `fonctionnement: { lit: { produits: "produits de la boutique, catégorie category, limite limit" } }` ; le nom (`produits`) se lit ensuite dans la forme comme une donnée : `- grille de produits, 3 colonnes:` puis les champs de l'élément (`name`, `price_text`, `stock_text`, `in_stock`…), `- si in_stock:`, `- ajout au panier: id, category`. Sources : produits de la boutique (catégorie, vedettes, tri, limite), produit de la page, produits voisins (limite), panier du visiteur, saisie de la commande (précisions), commande de la page, état du registre (registre), horaires du moment (jours, fuseau), consultations récentes (limite, types). Valeur d'un paramètre : une donnée du composant, un nombre, oui, non ou « un texte ». En tête de forme, `section, seulement si produits:` n'affiche rien quand la lecture est vide. Champs d'une source : `node bin/sitec.js explain "panier du visiteur"`. Une source est un service du compilateur : n'en invente pas, et n'écris pas de PHP pour en créer une. Cas de test : ajoute `à la visite: { produits: [ { id, name, price, price_text, max_qty, … } ] }` dans `fixtures/<cas>.yaml`. La page qui contient le composant n'est plus servie depuis le cache statique.
- **Places limitées, inscription unique, liste d'attente** : ce sont des règles du registre d'un formulaire, que le serveur applique à l'enregistrement, un envoi à la fois. Dans `fonctionnement: formulaire:`, à côté de « enregistre dans: stages » : « places: 12 » ou « places: 12 par seance » (un champ obligatoire qui groupe, de préférence à choix) ou « places: 12 par seance, comptées par personnes » (un champ nombre obligatoire) ; « si complet: message de refus » ou « liste d'attente: message à qui est mis en attente » ; « une fois par: email » ou « une fois par: email, seance » ; « si déjà inscrit: message ». Pour afficher les places restantes : `lit: { places: état du registre }` puis `- badge: places.left_text`, ou `- liste de places.groups:` avec `value` et `left_text` quand les places se comptent par groupe ; depuis un autre composant : « état du registre, registre stages ». Le client annule un envoi, le rétablit ou donne la place à un envoi en attente dans le back-office, onglet « Formulaires ». N'invente jamais un nombre de places : s'il n'est pas dans le brief, écris `[à compléter]` dans le texte et demande-le. Pas de date limite ni de paiement dans ces règles.
- **Composant écrit comme un document** (prototype) : `components/<nom>/document.md` à la place de `manifest.yaml`, en phrases, pour une section à formulaire avec registre (titre, champs, bouton, messages, places, liste d'attente, inscription unique, e-mail au site, places restantes). Le compilateur le lit sans modèle : `node bin/sitec.js lire <dossier>` redit chaque phrase comme elle est comprise, `--accepter` fige cette lecture dans `lecture.yaml` (suivi dans git, jamais modifié à la main). Une phrase dont un mot n'a pas de rôle, ou qui se lit de deux façons, est refusée (`E_DOCUMENT`, à la ligne du document) : reprends-la d'après la tournure citée, ne la contourne pas. Un document modifié sans relecture arrête `check` (`E_READING`). Un nombre, une négation, un destinataire ne sont jamais devinés. Tournures : `node bin/sitec.js lire --tournures`. Hors de ce domaine, écris le format langage.
- **Vocabulaire** (`vocabulaire.yaml` à la racine du site, ou d'un paquet) : quand il manque un élément aux primitives, définis un mot plutôt que de passer tout le composant au format html. `mots: { carte de visite: { description (obligatoire), données: { nom: texte, role: "texte, facultatif" }, forme: [ - carte « fiche »: [ - sous-titre: nom, - texte discret: role ] ], apparence: { fiche: centré } } }`. Dans la forme d'un composant : `- carte de visite: name, job` (données dans l'ordre de la définition, obligatoires d'abord, `rien` pour en sauter une). Un mot dont la forme contient `- contenu` reçoit des éléments : `- encadré, title:` puis la liste. Si aucune primitive n'écrit le balisage voulu, le mot se définit par `gabarit: |` (fragment de gabarit neutre, sans script, qui ne lit que ses données, `site` et `page`) et `feuille: |` (chaque sélecteur commence par la classe du mot : `.carte-de-visite…`). Un mot ne redéfinit ni une primitive ni un mot existant, n'a ni formulaire ni comportement nouveau. Mot de paquet : sans préfixe dans le paquet, `- vitrine.mention: note` depuis le site. Mots natifs : ligne de tarif, adresse, itinéraire, carte à la demande, carte de collection, état d'ouverture, tableau des horaires, consultation récente, événement d'achat, événement de vue de produit, événement de début de commande, aperçu de produit, reçu de commande, carte de produit, ajout au panier, fiche de produit, tableau du panier, totaux du panier, formulaire de commande, récapitulatif du panier, contact en colonnes, formulaire de contact, coordonnées du site. Liste : `catalog <dossier>` ; définition : `node bin/sitec.js explain "carte de visite" <dossier>`. Erreur de définition : `E_WORD`, à la ligne de `vocabulaire.yaml`, dite une seule fois ; erreur d'emploi : à la ligne du manifeste.
- **Composants de projet** (`components/<nom>/` dans le site) : `manifest.yaml` (même format que le catalogue : name, description, props, example, intents, effects), `template.html` (gabarit neutre, **jamais de PHP**), `styles.css`, `module.js`. Squelette : `node bin/sitec.js component new <dossier> <nom>`. Gabarit : `{{ p.title }}` (échappé), `{% if %}`, `{% for it in p.items %}` (`loop.index`, `loop.first`), `{% set %}`, fonctions `link(p.cta, 'btn')`, `img(p.image, p.title, '50vw')`, `icon(it.icon)`, `paragraphs(p.text)`. Variables : p, site, page, item, product, order, form, loop, cart, shop. `check` refuse une prop absente du manifeste, une variable inconnue, une balise non fermée, avec la ligne.
- **Paquets de composants** : `packages: [ ./paquets/vitrine ]` à la racine de `site.yaml` (chemin, ou nom d'un paquet installé dans `node_modules/`). Un paquet : `package.yaml` (`name` = préfixe), `components/<nom>/`, `components.yaml`, `vocabulaire.yaml`. Ses composants et ses mots s'utilisent préfixés : `- vitrine.encart: { title: … }`. Liste : `catalog <dossier>`, fiche : `explain vitrine.encart <dossier>`.
- **Tests de composants** : `components/<nom>/fixtures/<cas>.yaml` (props, plus `à la visite:` pour un composant qui lit) ; `node bin/sitec.js test <dossier>` rend chaque cas et le compare à `<cas>.html` (créé au premier passage, `--update` pour accepter un changement voulu). À lancer après toute modification d'un gabarit.
- **Éditeur** : `node bin/sitec.js schema <dossier>` écrit les schémas JSON du site (`.devanture/schema/`) et les branche sur l'extension YAML de VS Code (`.vscode/settings.json`) : complétion des composants (natifs, du projet, des paquets, composés) et de leurs props, documentation au survol, noms d'images et routes proposés, erreurs soulignées à la frappe. Les dépôts créés par `init` le font après chaque `npm install`. À relancer après l'ajout d'un composant, d'une collection ou d'une image.
- **Migration** : `node bin/sitec.js migrate <dossier>` (ou `--dry-run`) met le site à la dernière version du langage et liste des suggestions (coordonnées recopiées, valeurs à mettre en constantes).
- **CSS des composants** (projet et paquets) : chaque sélecteur commence par une classe préfixée du nom du composant (`.devis-express`, `.devis-express-carte`), jamais de sélecteur global ; couleurs et polices par les jetons (`var(--color-primary)`, `var(--color-success)`, `var(--color-warning)`, `var(--color-danger)`, `var(--font-heading)`) ; pas d'`@import`, de police ni d'image externe. `check` refuse (`E_CSS`) ou avertit (`W_CSS`).
- **Comportements déclarés** : pas de JavaScript dans un composant. `behaviors: [toggle | tabs | carousel | lightbox | filter | map | copy]` dans le manifeste, et les attributs dans le gabarit : `data-sl-tabs` / `data-sl-tab="a"` / `data-sl-panel="a"`, `data-sl-carousel` / `data-sl-track` / `data-sl-prev` / `data-sl-next`, `data-sl-toggle="id"`, `data-sl-lightbox`, `data-sl-filters` / `data-sl-filter="x"` / `data-sl-filter-item="x y"`, `data-sl-map="latitude,longitude,zoom"` (carte chargée au clic), `data-sl-copy="texte"`. Au format langage, les primitives et le mot `carte à la demande` posent ces attributs : rien à déclarer. Détail : `explain langage`, `docs/LANGAGE.md`. `<script>` et `onclick=` sont refusés dans un gabarit.
- **Composant décrit en langage naturel** : `node bin/sitec.js component new <dossier> <nom> --describe "…"` fait écrire et vérifier le composant par Claude (clé d'API requise ; sinon `--export p.json`, réponse d'un modèle, `--import r.json`). Relis le résultat comme un composant écrit à la main : la vérification garantit qu'il est valide et sûr, pas qu'il est beau ; ouvre son aperçu (`node bin/sitec.js component preview <dossier> <nom>`, page dans `.devanture/preview/`). Pour le changer : `component edit <dossier> <nom> --ask "…"` (restauré si la modification ne passe pas). `--package ./paquets/x` pour écrire dans un paquet.
- **Effets déclarés** (format html ; au format langage, écrivez le bloc `fonctionnement`, qui les produit) : dans le manifeste d'un composant de projet, `effects: { form: { store: devis, notify: true, success: Merci…, fields: [ name, phone, { name: type, label: Type, type: select, options: [A, B], required: true }, message ] } }` ; dans le gabarit `{% form %} {{ field('name') }} … <button class="btn">Envoyer</button> {% endform %}` et `{% if form.ok %}{{ form.success }}{% endif %}`, `form.failed`, `form.message`. Le compilateur fournit validation, CSRF, pot de miel, enregistrement (onglet « Formulaires » du back-office, CSV), e-mail. C'est la voie normale pour un formulaire qui n'est pas le contact : `custom` n'est plus nécessaire pour ça.
- **Icônes** (`features`) : 32 pictogrammes SVG, liste exacte dans `explain features` (dont scale, bread, croissant, cake, drop, flame, wrench, users, euro, pin, calendar). Un nom hors liste est une erreur.
- **Balisage léger** dans `richtext`, les réponses de `faq`, `access` de `map` : `**gras**`, `*italique*`, `[texte](/lien)`, et une ligne vide puis des lignes `- ` pour une liste. Rien d'autre (pas de HTML).
- **Composants d'accès et de récit** : `map` (adresse, itinéraire, carte OpenStreetMap chargée au clic si `lat`/`lon`), `steps` (étapes numérotées), `timeline` (dates clés).
- **Recherche qui répond** : la carte de réponse en tête des résultats vient des données compilées (horaires calculés à la visite, prix, coordonnées, réponses de FAQ). Un résultat « contact » envoie vers le formulaire prérempli avec la question (`?q=`).
- **Exploitation (hors DSL, rien à écrire dans le YAML)** : le site compilé embarque un back-office sur `/_admin` (messages, commandes et statuts, stock restant, mesures, intégrité, cache), activé par `ADMIN_TOKEN` dans `.env`. Les e-mails (formulaire, commandes) partent par le `mail()` de l'hébergement depuis `no-reply@<domaine>` (ou `MAIL_FROM` dans `.env`) ; le statut d'envoi est visible dans le back-office. Il ne modifie jamais le contenu : un texte, un prix ou un horaire se change dans le YAML puis se recompile. Les données d'exploitation vont en SQLite si PDO SQLite existe, en fichiers JSONL sinon (`STORE=jsonl` pour forcer) ; `data/` et `.env` survivent aux recompilations et aux déploiements.
- **Statique d'abord** : une page sans formulaire, panier, horaires, composant qui lit à la visite, bloc libre ni variante dépendant de l'appareil est servie depuis `cache/` aux visiteurs sans cookie, par Apache directement (`.htaccess` généré) ; les autres passent par PHP. Désactivable par `site.static: { enabled: false }`. Le `.htaccess` généré est vérifié sous un vrai Apache (`node scripts/verify-apache.mjs <dist> <port>`, Docker requis). Les sections à `variants` se rafraîchissent côté client via `/_fragment` quand le profil du visiteur change, sans recharger la page.
- **Hors ligne** : `site.offline: { enabled: true, short_name, theme_color }` émet un service worker (assets et versions texte consultables hors connexion, jamais les pages elles-mêmes), `offline.html` et `manifest.webmanifest`. Les assets sont versionnés par empreinte avec attribut `integrity`.
- **Déploiement signé** : `node bin/sitec.js deploy <dossier> --to https://domaine --secret s` pousse `dist/` vers `/_deploy` (HMAC, horodatage, vérification de chaque fichier contre `manifest.sha256.json`, fichiers obsolètes supprimés, données conservées). Le même secret est `DEPLOY_SECRET` dans le `.env` du serveur. Vérification d'intégrité à tout moment : onglet du back-office ou `php lib/integrity.php`.
- **Atelier navigateur** : `studio/index.html` (après `node scripts/build-studio.mjs`) fait tourner le même compilateur dans le navigateur : ouvrir un dossier de projet ou un exemple, éditer le YAML, vérifier, compiler en mémoire, télécharger `dist.zip`, et déployer vers `/_deploy` d'un site par envoi signé. Même sortie que la ligne de commande. Avec `site.studio: { enabled: true }`, le site compilé embarque cet atelier et sa propre source sur `/_studio` (derrière `ADMIN_TOKEN`) : le client édite et redéploie depuis son site, qui emporte alors la nouvelle source.
- **Dépôt de site sans PHP** : `node bin/sitec.js init <dossier> [--name "Nom"] [--repo github:compte/depot#tag | --local] [--no-git]` crée un dépôt git prêt : squelette YAML avec `[à compléter]`, `brief.md`, `README.md`, `CLAUDE.md` adapté (`npx sitec …`), `.gitignore` (dist/, .env), `package.json` (compilateur en dépendance : `github:dtdagames/devanture#v0.13.0` par défaut) et un flux GitHub Actions qui refuse tout fichier PHP, vérifie à chaque push, relit contre le brief et déploie par envoi signé sur `main` (variable `SITE_URL`, secret `DEPLOY_SECRET`). Le bloc `custom` y est interdit.
- **Plusieurs sites sur un hébergement** : un dossier avec `hosts.yaml` (`sites: [ { domain, aliases: [www…], project: ../chemin } ]`) et `node bin/sitec.js host <dossier>` compile tout dans un seul `dist/` routé par domaine, chaque site gardant ses données et son `.env` sous `sites/<nom>/`.
- **Porte de sortie** : `- custom: { php: custom/bloc.php, css: custom/bloc.css, props: { … } }` inclut un fichier PHP du projet. `check` l'accepte avec un avertissement `W_CUSTOM` : son contenu n'est pas validé. À n'utiliser que si ni un composant composé, ni un composant de projet (forme, lectures à la visite, formulaire déclaré) ne suffit, c'est-à-dire pour un traitement serveur inédit (un état qui demande plus que compter, grouper et dédoublonner les envois d'un formulaire) ; le signaler dans ton rapport. Interdit dans les dépôts créés par `sitec init`.
- `check` renvoie des erreurs JSON avec `path`, `expected`, `hint` et parfois `fix`. Applique-les puis relance `check`.
- Ne lis pas le code source du compilateur ni des composants : `catalog` et `explain` suffisent.
